CityOS (Civitas AI)

An Autonomous Multi-Agent Decision Intelligence Platform for Smart Cities

CityOS ingests real-time weather, air quality, traffic, and citizen data, reasons over it with a goal-driven multi-agent runtime backed by a Neo4j + Qdrant knowledge graph and NVIDIA Nemotron models via OpenRouter, and surfaces explainable, human-approved decisions through a Decision Workspace dashboard — real data only, in English or Vietnamese.

The Local Problem

City operators don't need another dashboard. They need a system that reasons.

Urban management in Hanoi runs on data that never sits still — a sudden downpour, a spike in PM2.5, a traffic jam forming three streets over, a cluster of citizen complaints, a crowd gathering for an unplanned event. A static dashboard can put all of that on a screen as numbers. It can't tell an operator which signal matters right now, why it matters, or what to actually do about it.

That's the judgment call an operator has to make in real time: close a road, or open a cooling station? Every option carries the same risk — either reacting too slowly, or trusting an opaque system that can't explain itself once the decision turns out to matter. What Hanoi's operators need isn't one more chart. It's a system built to reason about these signals together, and to explain the reasoning behind whatever it recommends.

The Story of Building It

One rule shaped every decision: never a black box

We built CityOS around a single non-negotiable: when an AI system is recommending action for a real emergency, "trust me" isn't good enough. Every agent in the pipeline — Traffic, Environment, Emergency, Citizen, Knowledge — has to cite the specific evidence behind its input: a source, a data point, a timestamp, a confidence score. Never just a judgment call it made on its own.

Traffic Agent

Cites live congestion and incident data instead of guessing at road conditions.

Environment Agent

Cites real, timestamped AQI and weather readings instead of asserting a risk level.

Emergency Agent

Cites matched knowledge-graph precedent before recommending an emergency action.

That principle ended up shaping the whole project, not just the agents: a rule-based Critic that checks evidence for sufficiency before anything reaches a human, and a hard rule against fabricated metrics. The agents run against real Open-Meteo/OpenAQ feeds and a real Neo4j + Qdrant knowledge graph — not seeded fixtures dressed up for a screenshot.

How the Prototype Works

A goal doesn't run straight through an LLM

When an operator submits a goal, it isn't handed straight to a language model. A Planner first breaks it down into a dependency-aware task graph — separate, parallel workflows for whatever pieces don't depend on each other.

Planner
→
Traffic / Emergency / Knowledge Workers (parallel)
→
Reflection + Critic
→
Decision
→
Human Approval

Real data in, evidence out

Each worker agent pulls real data before it says anything — live weather and AQI readings from the Open-Meteo/OpenAQ APIs, and structured facts from the Neo4j + Qdrant knowledge graph — and cites exactly what it used: source, type, confidence, timestamp, instead of a prose conclusion. A rule-based Critic (not another LLM call) then reviews that evidence for sufficiency and unsupported claims; a weak or contradicted decision automatically routes to human approval rather than shipping silently. Nothing executes until an operator approves it.

Outcomes are measured, not claimed

Every goal persists a Decision Session through its full lifecycle — collecting → analyzing → recommend → awaiting approval → observing → evaluated. At approval, a real baseline CityScore is captured. After a delay (or on demand via Check Outcome Now), the observed CityScore is compared against that baseline, so "did this decision help" is a measured answer, not an assumed one.

Architecture Overview

Four layers, one decision loop

The frontend never talks to an LLM directly, the agent runtimes never write to Postgres directly, and no agent calls an AI provider directly — each layer only knows about the one below it.

Frontend — Stitch Shell

React + TypeScript dashboard. Decision Workspace, Decision Sessions, City Intelligence, Knowledge Graph, Reports, Settings — real backend data only, English/Vietnamese.

FastAPI Backend

REST + WebSocket API. Routes goals/simulations to the agent runtimes, streams live progress, serves CityScore/AQI/decision-history reads.

Multi-Agent Runtime

v1 sequential pipeline + v2 event-driven Planner → Workers → Reflection → Decision, gated by human approval.

Knowledge + AI Gateway

Neo4j + Qdrant knowledge graph; NVIDIA Nemotron via OpenRouter behind a single gateway, Gemini fallback.

Data Layer

PostgreSQL (sensor readings, decisions, sessions) · Open-Meteo + OpenAQ (real per-district weather/AQI, refreshed every 15 minutes)

Knowledge Layer

A knowledge graph the agents actually query

City-specific knowledge doesn't live in a prompt template — it's ingested once and queried live.

OpenStreetMap Wikipedia Wikidata GeoJSON district boundaries Government PDFs

These sources are chunked, embedded, and indexed into Neo4j (an entity/relation graph) and Qdrant (a vector store), retrieved through a full embed → search → rerank pipeline. The Knowledge Agent doesn't just write to the graph — it extracts keywords from the current goal, queries Neo4j for related entities and relations, and folds real graph facts into both its reasoning context and its cited evidence.
